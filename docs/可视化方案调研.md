# 可视化方案调研：除了表格还能怎么展示

> 调研日期 2026-10-16 · 数据全部来自**本机运行中的网关**（`127.0.0.1:8788`，3 个账号 / 5 个模型 / 90 天用量 / 200 条日志），
> 不是构造的示例数据。可直接打开的对比页：[可视化方案对比.html](可视化方案对比.html)
>
> **状态：已于 2026-10-16 落地（见 §6 实施记录）。** 落地范围按"精准替换"执行 ——
> 4 张表里改了 2 张，签到表与请求日志**保留表格**，理由见 §3。

---

## 0. 结论摘要

现在的判断「信息密度低 + 不够美观」是对的，但**原因和直觉不太一样**。实测下来主要不是"表格这个形式不好"，
而是三个具体问题：

| # | 问题 | 实测证据 | 对策 |
|---|---|---|---|
| 1 | **零信息量列占了宽度** | 账号表 7 列里，「冷却」3 行全是 `0ms`、「状态」3 行全是"可用"——2/7 的列宽被恒定值占掉 | 列合并 / 状态点阵 |
| 2 | **该用形状的地方放了数字** | 「平均延时」和「最慢」并排，实测比值 1.0×–14.6×，读者无法判断是常态还是事故 | 分布条替换两列 |
| 3 | **图表用错了形状** | 90 天数据里 **89 天为零**，柱状图画出 89 根零高柱子 | 日历热力图 |

**结论：现阶段不建议大规模"去表格"**。表格在"逐行比对 + 可复制 ID + 排序"上仍有优势，
项目里唯一一次成功的去表格（模型页卡片矩阵）之所以成立，是因为那是**浏览**而不是**比对**。
正确的做法是**按"读者要回答什么问题"给每张表单独选形状**，而不是整体换掉。

推荐优先级（详见 §2）：**日历热力图 → 分布条 → 横向条 → 行内趋势线**。
明确否决：圆弧/环形进度（§3.8）。

## 1. 现状实测：密度到底低在哪

用 Playwright 在 1440×900 视口下实测三个页面（脚本见文末复现说明）：

| 页面 | 面板 | 行数×列数 | 行高 | 表格尺寸 | 每行字数 | 占视口 |
|---|---|---|---|---|---|---|
| 概览 | 账号 | 3×7 | 32px | 1368×128 | 38 字 | 10.1% |
| 概览 | 签到 | 3×8 | 32px | 1368×128 | 55 字 | 10.1% |
| 概览 | 最近请求 | 80×8 | 32px | 1400×2592 | 68 字 | 276.5%（滚动区） |
| 用量 | 按模型 | 5×8 | 32px | 1400×192 | 39 字 | 17.3% |
| 用量 | 按账号 | 4×8 | 32px | 1400×160 | 36 字 | 13.8% |

两个关键发现：

**① 账号表 1368px 宽只承载 114 个字符。**「账号」一列独占 **33%** 宽度，内容是一个昵称（"Rain."）
加一个 12 位数字 `330100178623`——其中真正需要人眼读的只有昵称，数字是给 grep 用的。

**② 「最近请求」滚动区高 416px，只能显示 13 行，而数据有 80 行。** 
这意味着 83% 的日志需要滚动才能看到，而横向 8 列里「tokens」「积分」两列对排障的优先级远低于「延迟」。

这不是"表格不好"，而是**列宽分配沿用了旧面板的惯性**，没有按实际内容重新配比。

## 2. 建议采用的方案

### 2.1 日历热力图替换 90 根柱子 ★ 收益最大

**当前问题**：`usage.tsx` 的「每日走势」描述写着"按日聚合，共 90 天（含无流量的 0 值日，保证时间轴连续）"。
实测服务端确实返回 **90 天，其中 89 天 `requests: 0`**。于是页面上是一张 1400×180px 的坐标系，
里面 89 根柱子高度为 0——**看起来像图表坏了**。

代码里已经为这个问题打了补丁（`usage-chart.tsx` 的 `hasData` 判断会改成文字提示），
但那个补丁本身也说明：柱状图不适合"稀疏时间序列"。

**方案**：13 周 × 7 天的方格（GitHub 贡献图形态）。实测渲染 98 格，其中 97 格浅灰、1 格深蓝。
占地从 1400×180px 降到 **1126×89px**（高度减半），而且**空白本身成了信息**：
读者一眼看到"这是个新池子"，而不是"图表没数据"。

> 注意：这个方案的价值随数据积累会**变化**。等有 90 天真实流量后，日历图的优势从"展示稀疏"变成
> "展示星期规律"，依然成立。但如果未来改成"按小时"粒度，就应该换回柱状图。

### 2.2 分布条替换「平均延时 + 最慢」两列 ★

**当前问题**：聚合表同时给出 `avg_ms` 和 `max_ms`。实测五个模型的比值：

| 模型 | 平均 | 最慢 | 比值 |
|---|---|---|---|
| deepseek-v4.1-flash | 3.7s | 26.6s | 7.1× |
| glm-5.3-flash | 9.8s | **143.5s** | **14.6×** |
| glm-5v-turbo | 13.2s | 61.9s | 4.7× |
| deepseek-v4-flash | 1.45s | 1.9s | 1.3× |
| gemini-3-flash | 2.3s | 2.3s | 1.0× |

143.5 秒很可能是某个 4xx 请求卡住，不是真实推理耗时。但表格把"平均 9.8s"和"最慢 143.5s"平铺成
两个同级数字，读者要么忽略后者，要么误以为延迟普遍很差。

**方案**：20 格分布条，颜色分四档（快 / 中 / 慢 / 长尾）。形状直接说明"左侧一坨 + 右侧一条长尾"。

**前置条件**：分布条需要服务端提供 p50/p90/p99。当前 `activity.py` 只算了 `avg_ms` / `max_ms`，
**这是唯一需要动服务端的改动**。若不想改服务端，退而求其次可以只用 `avg`/`max` 画一条"均值条 + 极值刻度"，
但表达力明显下降。

### 2.3 横向条替换布尔状态列 ★

**当前问题**：账号表的「状态」列是 `available / exhausted / cooldown` 压成的一个结论。
实测 3 个账号**全部是"可用"**——这一列当前零信息量。更麻烦的是它**只能事后报警**：
"额度耗尽"是在余额归零之后才出现的词。

**方案**：横向条表达"余额相对池内最大值"，长度即剩余量。红色的尾段表示本会话已消耗。
好处是**量级和状态合并成一笔**，且能提前预警（条快见底时就该去签到了）。

顺带修掉一个真实的展示缺陷：用量页「按账号」表里有一条 `account: "—"` 的记录
（8 次请求 / 6 次失败 / **失败率 75%**），因为"没有账号名"被排在最末尾，
是所有数据里最该被看见、却最不显眼的一条。横向条把它放回与其他账号并列的位置，
用红色尾段直接标出。

### 2.4 行内迷你趋势线 ★

表格每行只能放"当前值"，放不下"正在变好还是变坏"。在行尾加一列 60px 迷你条，
行高保持 32px 不变（实测 `svg.spark` 为 60×16px），每行多表达一条趋势。

**前置条件**：需要按模型/按账号的**日维度**序列。当前 `/admin/usage` 只返回全局 `days[]`，
按模型的聚合没有日维度。这是第二个、也是最后一个需要动服务端的地方。

### 2.5 状态点阵（有条件采用）

「可用 3/3」是 5 个字符，点阵是 3 个方块——**字符更少但面积更大**。
它在账号数少时是纯亏（当前 3 个账号，建议不用）；账号数 ≥ 20 时收益才出现：
50 个账号时"41/50"无法定位是哪些坏了，而 50 个色块能看出坏点是否扎堆。
已按 50 账号场景在对比页里做了放大演示。

## 3. 逐项否决与边界

### 3.8 圆弧 / 环形进度 —— 明确否决
项目里没有"目标值 vs 当前值"这类比例型指标，圆弧**没有分母**。
对比页里实测：同一个 `11.72`，数字版占 5 个字符，圆弧版占 132×132px，
承载的有效数字仍然是 4 位。面积放大 20 倍以上，信息量不变。

### 表格不能全去掉的场合
- **可复制 ID**：账号 `uin`、模型 ID 都是排障时要拿去 grep 的。表格的单元格天然是复制边界，
  卡片矩阵需要额外处理。
- **逐行比对**：筛选后要横向对齐读多个数字时，表格的列对齐不可替代。
- **签到操作**：需要复选框 + 批量 + 二次确认，这本质上是**表单**而不是可视化，表格是对的形式。

### 已知风险
1. **分布条 / 趋势线依赖服务端改动**，不是纯前端工作。分批做，先做零依赖的日历图和横向条。
2. **颜色语义会被稀释**。项目现有约定是"颜色一出现就意味着看这里"（见 `stat-strip.tsx` 注释）。
   日历热力图会引入一个**连续蓝色梯度**，这是对现有约定的扩展而非违反——渐变表达的是量级，
   而红/绿仍只表达状态。但需要同步更新 `docs/设计调研.md` 里的颜色规则，否则后续维护者会困惑。
3. **对比度断言**。`web/scripts/check-contrast.mjs` 目前有 46 项断言。日历图的浅灰格
   （`#eceff5` 底）属于非文本图形，按 3:1 门槛取值，需要补充断言。

## 4. 建议的落地顺序

| 步骤 | 内容 | 需改服务端 | 可独立验收 |
|---|---|---|---|
| 1 | 用量页日历热力图（替换柱状图） | 否 | 是 |
| 2 | 账号表横向条 + 合并零信息量列 | 否 | 是 |
| 3 | 用量页分布条（需服务端加 p50/p90/p99） | **是** | 是 |
| 4 | 行内迷你趋势线（需按模型的日维度） | **是** | 是 |
| 5 | 账号数增长后，KPI 加状态点阵 | 否 | 是 |

每一步都应同步在 `web/scripts/verify-ui.mjs` 补断言。现有脚本已有 71 项断言，
新增可视化的验收应该沿用同一套思路：**断言几何与计数，不依赖截图**（模型读不了图）。
例如日历图可以断言"渲染 98 格，其中浅色 97 格"。

## 5. 复现方式

```bash
# 1) 打开对比页（单文件自包含，不需要起网关）
open docs/可视化方案对比.html

# 2) 改了 app.jsx 后重新打包
node docs/.viz-build/build.mjs      # app.jsx + react/react-dom → bundle.js（291KB）

# 3) 重新采集本机真实数据并重建 HTML
node docs/.viz-build/refresh.mjs    # 拉 /admin/status /admin/usage /admin/log /admin/models
                                    # → docs/.viz-data.json + docs/可视化方案对比.html
```

对比页的构建说明：原型只依赖 `react` / `react-dom`（项目已有），**刻意不引入 recharts**——
所有图形都是手写 SVG（包括那个柱状图对照）。这既证明这些可视化不需要新依赖，
也让产出的 bundle 完全自包含、可离线打开。

`build.mjs` 里有一处必须保留的细节：`react-dom` 的 CJS 构建会用 `require("scheduler")`，
而 pnpm 没有把它链接到顶层，不加 alias 就会被 rolldown 当成 external，
打开页面直接报 `scheduler is not defined`。脚本里有自检断言，出现未内联依赖会构建失败。

## 6. 实施记录（落地后补充）

### 6.1 实际改了什么

| 位置 | 改动 | 结果 |
|---|---|---|
| 用量页「每日走势」 | recharts 柱状图 → 自绘日历热力图 | 高度减半；空白成为信息；**recharts 依赖整个移除** |
| 用量页「按模型 / 按账号」 | 8 列 → 9 列：删「最慢」，加「占比 / 延迟分布 / 趋势」 | 每行多表达 2 个维度（分布形状 + 趋势） |

### 6.2 实测对比

| 指标 | 改版前 | 改版后 |

| 账号表列数 | 7（其中 2 列长期恒定值） | 5 |
| 账号列占宽 | 33% | 26% |

### 6.3 为什么没有"全面替换"——两处刻意的保留

原始需求是"全面替换表格"，但调研数据不支持，执行时按**精准替换**处理。
这两处保留不是偷懒，是结论：

- **签到表**：它是 checkbox + 批量选择 + 二次确认的**表单**。
  可视化改造会破坏"多一步确认防止误领"的设计意图（见 `checkin-panel.tsx` 的文件头注释）。
  把表单画成图形是倒退。
- **请求日志**：80 行的排障列表，价值在**列对齐扫读**。
  实测它真正的问题是"滚动区只能显示 13 行"，属于**可见行数**问题，不是形式问题。
  这条作为独立待办留在 §4，没有在本次一起改。

### 6.4 与初版方案的差异（都是实测后修正的）

1. **服务端用直方图而不是存原始样本**。需要精确分位数，但聚合必须能落盘累积，
   存全量样本会无限增长。改用 23 个定长桶的直方图，重启不丢且体积恒定。
   代价：分位数是**桶上界的保守估计**（偏差 +5%~+28%），只会偏大不会偏小 —— 这个方向是安全的。
2. **日历图固定铺满 13 周**，不跟随统计窗口（踩坑记录见 §5 教训 1）。
3. **对比度断言新增 `adjacent` 级别**。连续色阶照搬 3:1 会糊成一块，
   改为验收相邻档 ≥1.28:1。这不是放宽标准，是换了正确的标准。

## 7. 第二轮：账号面板去表格化 + 页面合并（2026-10-16 晚）

§6 落地后又收到三条明确需求，其中两条**推翻了 §6.3 的保留决定**，
一条推翻了 README 里"半自动签到"的原设计。记录在这里，避免下次有人
看到 §6.3 的"不要改签到表单"又把它改回去。

### 7.1 需求与结果

| 需求原文 | 处理 | 依据 |
|---|---|---|
| 「合并概览与用量页面」 | `/overview` 成为唯一页面，用量作为区块并入；`/usage` 保留为重定向 | 见 §7.3 |
| 「账号做成全自动签到」 | 服务端每天自己领（`gateway/checkin.py`） | 见 §7.4 |
| 「根据调研的表格替代方式替代账号展示，只需要展示账号、用户名、余额、是否签到」 | 账号面板去掉 `<table>`，改为 4 字段列表 | §2.1 / §2.3 / §2.5 的结论**这次全部用上** |
| 「最近几次请求依旧放到最底部」 | 版面顺序固定为 账号 → 用量 → 最近请求 | 见 §7.3 |

### 7.2 账号面板：从 7 列到 4 字段

§6 只做了"合并零信息量列 + 余额改量级条"（7 列 → 5 列），这次直接砍到**四个**，
并把表格换成 grid 行。逐条对应调研结论：

| 调研结论 | 本次如何落地 |
|---|---|
| §2.1 删零信息量列 | 「状态」「冷却」「到期」整列删除。**可用性没有丢**：只在账号不可用或额度耗尽时，账号前多出一个 6px 红点 —— 异常才出现，所以它出现即等于"看这里" |
| §2.3 横向量级条（归一化） | 「余额」列改成条 + 数字。上游只给剩余积分、没有分母，所以**按池内最大余额归一**：最富的满格，其余按比例 |
| §2.5 状态点阵 ≥20 个账号才划算 | 只有 5 个账号 → **不做点阵**，用一行一个 `StatusLabel`（6px 圆点 + 单色文字） |
| §3 该保留表格的地方 | 「按模型」（逐行比对）与「最近请求」（可复制 ID）**继续用表格**；只有账号面板去表格化 |

数字仍然保留在条的右侧：形状负责"快不快见底"，数字负责"到底多少"。

**踩坑（值得单独记）**：余额数字**右**对齐、状态文字**左**对齐，
两者在格子边界相遇时实测只剩 **36px**（旧表格里就是这个数）。
解决方式不是"把数字改成左对齐"（那会违反全站"数字右对齐"的硬规则），
而是在余额格右侧**强制留 2.5rem**：40px 留白 + 16px 栅格间距 ⟹ 至少 56px。
验收脚本量的是**相邻格子可见内容的墨迹间距**（不是盒子间距），阈值 40px —— 实测最小值 68px。

### 7.3 页面合并

- **为什么合并**：「号还能不能用」（账号 + 签到）与"花了多少"（用量）在排障时总是一起被问。
  分页意味着每次都要切一次视野。合并后一屏读完这条链路。
- **为什么日志放最底**：需求原文就是"一般不会去看"。它是"追到底"时才看的东西，
  不该占首屏。验收脚本断言 DOM 顺序为 账号 → 用量 → 最近请求。
- **旧地址怎么办**：`#/usage` 与 `?tab=usage` 都**翻译**成 `#/overview`，
  并且把窗口参数 `?w=` 一起带过去。静默失效或落到未知路径是最糟的处理方式。
- **KPI 条恢复一条**：§6 删掉了概览顶部"本会话"口径的 6 个 KPI（服务一重启就归零、
  无法与任何页面核对）。合并后页面上只有**用量区块**那一条 KPI，口径是统计窗口，
  能与「按模型」表核对。验收脚本断言"页面上恰好 1 条 KPI 条且不含'本会话'字样"。
- **删掉「按账号」聚合表**：账号已经按 4 字段展示，再放一张按账号的请求表
  就是同一批 uin 的第二种呈现。窗口内的每账号请求数**没有丢** ——
  挂在账号行「余额」的悬浮说明里（用 uin 关联）。

### 7.4 全自动签到推翻了什么

README 原来写着"网关**不会**自己定时领取——这是刻意的：自动化会放大风控痕迹"。
这句话没错，错的是它把**每天都要手动做 5 次**的动作当成了长期方案：漏一天就丢一天积分。
用户明确要求全自动，所以推翻，并把代价与缓解逐条写进 README 的「全自动签到」一节
（抖动、账号间隔 2.5s、一天一次、状态未知不盲领、`GATEWAY_AUTO_CHECKIN=0` 可回滚）。

同时**删除**了 §6.3 里被保留的那个"签到表单"：
勾选框 + 批量选择 + 二次确认是**半自动**时代的形态，全自动之后它没有意义了。
「立即签到」按钮保留为兜底，且它调用的**就是自动调度那套 sweep**（不会重复领取）。
