# 账号轮换策略设计（反薅羊毛）

> 状态：设计已定稿，实现进行中。本文是 `gateway/rotation.py`、`gateway/pool.py`、
> `gateway/config.py`、`gateway/creds.py` 的**唯一契约来源**。代码与本文冲突时以本文为准，
> 或先改本文再改代码。

## 1. 问题：现状为什么在「薅羊毛」

现行选号逻辑在 `gateway/pool.py::Pool.candidates()`：

```python
def key(c: Credential):
    return (
        0 if c.cooldown_until <= now else 1,   # 可用优先
        -(self._credits.get(c.account_id, 0)), # 积分高优先  ← 问题在这
        -c.expires_at_ms,
    )
```

`pick()` 取排序后的**第一个**，于是行为退化成：

1. **单调倾泻**：只要 A 号积分最高，**每一个**请求都打到 A，直到 A 被限流
   （`cooldown_until`）或积分耗尽（`exhausted`）才轮到 B。
2. **额度最高的号最先被打空**：高额度账号承受 100% 负载，低额度账号几乎闲置，
   池子的**总可用额度被浪费**，而全局吞吐被单号限流卡死。
3. **无节流**：同一秒内并发 10 个请求可能全落在同一个号上，直接撞限流。
4. **重启即失忆**：`_credits`/`_spent`/`_requests` 只在进程内存里，重启后
   「谁用得多」这个信息归零，于是重启后又从同一个高额度号开始薅。
5. **失败才换号**：换号是**被动**的（失败→`report_failure`→`exclude`），
   而不是**主动**分摊。限流已经造成了用户可见的延迟和一次失败重试。

结论：这不是「轮换」，是「优先级队列」。要修的是**主动分摊**。

## 2. 设计目标与不变量

| 目标 | 可验证的判据 |
|---|---|
| G1 不连打同一个号 | 连续 2 次请求命中同一账号的比例显著下降；任意账号在 `MIN_INTERVAL_S` 内被再次选中即视为违规 |
| G2 长期用量与额度成正比 | 200 次请求后，各账号用量占比与其「可用额度占比」偏差在容差内 |
| G3 保护快见底的号 | 剩余额度 ÷ 消耗速率小的号优先被消耗（先把零头用掉，不浪费） |
| G4 不牺牲可用性 | 轮换只改变**选谁**，不改变「选不到就报错」的语义；限流/耗尽/过期照旧被排除 |
| G5 重启不失忆 | 每账号的累计消耗、请求数、上次使用时间落盘，重启后连续 |
| G6 零配置可跑 | `.env` 为空时全部走安全默认值，网关照常启动 |
| G7 可解释可调试 | 每次选号能回答「为什么是它」；测试可注入固定随机种子做到确定性 |

**核心不变量（Invariants）**，任何实现都不得违反：

- **I1** 轮换**只能收窄**候选集，不能放大。候选集上界永远是
  「`available()` 为真的账号 ∪ 冷却中的账号（作为最后一搏）」，
  与现在的语义完全一致。
- **I2** `client` 类错误的处理不变：换谁都一样，不换号（见
  `Pool.report_failure` 的 `return False` 分支）。
- **I3** 调度器**永不抛出**。任何内部异常都必须退化为「返回排序后的第一个候选」，
  否则一次选号异常会变成一次用户可见的 500。
- **I4** 在飞（in-flight）计数**必须**在 `finally` 中释放，包括客户端提前断开、
  流式传输中断、异常抛出等所有路径。泄漏会永久缩小池子。
  实现期细化为下面的 **认领/释放契约**。
- **I5** 调度器纯内存、无 I/O、可单测；落盘由 `creds.py` 负责，两者解耦。

### 2.1 认领/释放契约（实现期发现的最危险缺陷）

第 1 层的并发上限要求「检查 + 占坑」原子完成，否则 N 个并发请求会全部通过检查
（TOCTOU）。因此**由 `pick()` 在同一把锁内完成检查与 `in_flight += 1`**，
胜出者返回时名额已占好。这带来一个必须显式声明的生命周期契约：

> **契约：任何一次返回非 None 的 `pick()`，都必须在所有路径上被恰好释放一次。**

实现期间这里踩过两个坑，都记下来避免回归：

1. **双重计数**：`pick()` 占坑后，若 `Pool.note_request_started` 再 `+1`，
   而释放只走一次，则每个请求净泄漏 1 个槽位，池子最终缩到 0。
   → 因此 `note_request_started` **不占坑**，只做镜像对齐；
   计数权威来源是 `RotationScheduler.state(aid).in_flight`。
2. **释放被跳过**：`server.py::_note_finished` 曾在 `started=False` 时**跳过释放**。
   但 `pick()` 已经占坑，于是槽位永久泄漏。实测 3 账号 × cap 10 = 30 个槽位后
   `pick()` **永远返回 None**，网关报「没有可用账号」直到重启——
   比原来的薅羊毛更糟（池子直接死掉，而不是集中负载）。
   → 释放必须**无条件于 `started`**，且幂等（重复释放钳制在 0，绝不为负）。

**为什么要写进文档**：这两个坑都不会被「单账号顺序调用」的测试发现，
只有「不释放就必然耗尽」的断言才能锁住。见 §7 第 16 项。

## 3. 算法：三层调度

`RotationScheduler.pick(cands, credits, now, exclude, explore=False) -> Optional[Credential]`

### 第 1 层：硬过滤（Hard Filter）

依序剔除，**不做任何加权妥协**：

1. `cred.account_id in exclude`（本次请求已试过的号）
2. `not cred.available()`（耗尽 / 冷却中 / 凭据不可用）
3. `state.in_flight >= MAX_CONCURRENCY`（该号并发已达上限）
4. `now - state.last_used_at < MIN_INTERVAL_S`（最小间隔未到）
5. **基础套餐分级**（2026-10-17 新增，见 §3.1）：若还有账号基础套餐余额为正，
   则剔除基础套餐已耗尽的账号；全员耗尽时该条不生效。

第 1 层是**硬性**的，因为 3、4、5 都是**准入资格**的约束。一旦把它们降级成权重，
高额度账号的权重会再次压过它们，退化成原问题。

> 第 5 条的第一版被写在第 3 层（当成权重），结果**完全没有效果**——实测一个基础
> 套餐已归零的号仍分到约 16% 的流量。详见 §3.1，那一节是这次修正的完整记录。

若第 1 层后为空 → 返回 `None`（调用方 `Pool.pick` 决定是放宽区域还是报错）。

**关于第 4 条的兜底**：如果**所有**候选都卡在 `MIN_INTERVAL_S` 上，
则本层退化为只保留「`last_used_at` 最早的那一个」。这是必要的——
否则单账号池或高并发场景下会直接选不出号。这个兜底必须在实现里显式写出，
并由测试覆盖（见 §7 场景 4b）。

### 第 2 层：时间片轮转（Time-Slice Fairness）

先算出候选集中**最旧的** `last_used_at`：`oldest = min(last_used_at)`。
再设宽度 `W = max(SLICE_S, 2 × p95_recent_latency)`，其中延迟不可得时
直接取 `SLICE_S`。

剔除所有满足 `state.last_used_at > oldest + W` 的候选——即「刚刚才被用过、
而别人已经等了一整个时间片以上」的号。

**「等够了」的判据用 `W`，不是 `MIN_INTERVAL_S`（2026-10-17 修正）**。
旧实现在 `_waiting()` 里用 `age >= MIN_INTERVAL_S` 区分串行与突发，前提是
「串行 ⇒ 所有人年龄都 >= MIN_INTERVAL_S」。这个前提在 N 个号的池子里**永远不成立**：
N 个号轮流用，同一个号两次被用之间至少隔 N × 请求间隔。实测 N=6、请求间隔 6s 时
每号年龄约 36s（远大于 5s），于是 `waiting == 候选集` 恒成立，本层**从来没有筛掉过
任何号**。现在改用 `age >= W`（生产值 30s）：只有确实等满一个时间片的号会被留下，
都没等够时退回全量交给第 3 层。

**不许用 `or alive` 兜底收窄结果。** 旧代码里 `sliced or alive` 与 `waiting or alive`
两处兜底会在收窄结果为空时把整个集合放回去，让本层变成空操作——这是本层失效的
第二个成因。现在收窄结果理论上永不空（`oldest` 必然入选），万一被 NaN 污染则退回
**最久未用的那一个**，而不是全量。

**当 `explore=True` 时跳过本层**（用于探测/自检，想快速摸清各号健康状况）。

**当第 2 层后只剩 1 个候选时直接返回它**，不再往下加权——
避免在唯一候选上做无意义的随机化。

### 第 3 层：加权随机（Weighted Random）

对存活候选计算权重：

```
credit_share  = credits[c] / Σ credits[all alive]          # 剩余额度占比
runway_share  = runway(c) / Σ runway(all alive)            # 续航占比
coolness      = clamp(1 - (now - last_used_at[c]) / max_age, 0, 1)
                                                           # 越久没用越该用
base_share    = base[c] / Σ base[all alive]                # 基础套餐占比（仅同级别内微调）

weight = W_BASE * base_share + W_CREDIT * credit_share
       + W_RUNWAY * runway_share + W_COOL * coolness
```

`base_share` 只是**同级别之内的微调**（两个号基础都有剩时，基础多的略占优）。
它**不是**「基础套餐优先」这条策略的承重件——那条由第 1 层第 5 条负责，见 §3.1。

**`coolness` 必须钳制到 `[0, 1]`（实现期修正）**。本文早期版本写的是
`1 - (now - last_used_at) / max_age` 不钳制。这在长跑进程里会出大问题：
若 `now - last_used_at` 远大于 `max_age`（例如 1e5 秒 vs 30 秒的 `max_age`），
`coolness` 会变成约 `-3332`，而 `credit_share + runway_share` 最多只有
`W_CREDIT + W_RUNWAY = 3`，于是**总权重为负**，账号在加权抽样中被静默跳过——
健康账号反而拿不到流量。钳制后语义不变（年龄 ≥ `max_age` ⇒ `1.0`，即「最该用」）。
`max_age` 取候选集内 `last_used_at` 的实测跨度，取不到时退回 `SLICE_S`。

其中 `runway(c)`：

```
runway(c) = credits[c] / max(ema_cost_per_min[c], MIN_RATE)
```

- `ema_cost_per_min` 是指数加权移动平均的**每分钟**消耗速率，
  halflife = `EMA_HALFLIFE_S`（默认 900s，即 15 分钟）。
  用 halflife 而非固定窗口，是为了让「刚刚突然开始大额消耗」的号**立刻**降权。
- `MIN_RATE` 是**除零保护兼速率下限**（默认 0.01 积分/分钟）。没有它，
  一个「有额度但从未被用过」的号会得到 `runway = ∞`，独占全部权重。
- **无历史且额度未知** → `runway = 0.0`（降权，但**不**淘汰）。
  这是保守选择：说不清它有多少额度时，不优先押注它，但池子浅的时候仍可用它。

**权重全为 0 时退化为等概率**，保证第 3 层永远返回一个候选。

**为什么用加权随机而不是纯轮转**：纯轮转会让「剩 5 分」的号和「剩 5000 分」的号
被同等消耗，前者很快见底，池子的整体续航反而变短。加权随机在**统计意义上**
让用量与额度成正比（G2），同时保留 G3 的「先烧零头」倾向——这两者不矛盾：
`credit_share` 项负责总量比例，`runway_share` 项负责消耗**顺序**。

**`runway` 为什么比 `credit_share` 更能保护小号**：假设 A 剩 5000 分、
近期消耗 1000 分/分钟；B 剩 5 分、消耗 0.01 分/分钟。按额度占比 A 拿 99.9%，
但 A 只能再撑 5 分钟。按续航，B 能撑 500 分钟、A 只能撑 5 分钟，
于是先把 B 的零头烧掉——这正是「不浪费额度」想要的。

默认权重：`W_CREDIT = 1.0`、`W_RUNWAY = 2.0`、`W_COOL = 0.5`。
`runway` 给最高权重，因为它是唯一同时编码「有多少」和「还能撑多久」的项。

### 3.1 基础套餐积分优先：第一版为什么没生效（2026-10-17 修正）

**背景。** WorkBuddy 的余额是两个桶：**基础套餐积分**（月度订阅，月底清零）与
**平台奖励积分**（一次性赠送包，过期晚得多）。同样是 1 分，价值并不相同：
基础积分今天不用、月底就清零，是沉没成本；奖励积分可以留到下个月。所以
「优先使用基础套餐积分」的正确含义是：

> 优先把请求派给基础积分还有剩的号；只有在**池子里再没有基础积分**了的时候，
> 才让「基础已耗尽、只剩奖励积分」的号承接流量。

**现象。** 第一版把这条策略实现成第 3 层的一个加权项 `base_share`（`W_BASE=1.5`）。
上线后实测：账号 `330100178623` 的基础套餐（`CycleCapacityRemain`）已经是 **0**，
其余 5 个号都还有 298～500 的基础积分，但它在近 3 小时的 429 次请求里仍占 **18.2%**
——与「按总余额分摊」的结果一模一样。面板上是好是坏一眼能看出来：

| 账号 | 基础套餐 | 平台奖励 | 总余额 |
|---|---|---|---|
| 330100178623 | **0.0** | 1846.45 | 1846.45 |
| 330120998846 | 500.0 | 2009.71 | 2509.71 |
| 330127845755 | 298.49 | 2200.0 | 2498.49 |
| 330127927009 | 442.08 | 2200.0 | 2642.08 |
| 330127928044 | 442.44 | 2200.0 | 2642.44 |
| 330128259877 | 498.82 | 2100.0 | 2598.82 |

**根因有两层，都不是「权重没算对」。**

1. **加权项只改变概率，不改变资格。** `base_share` 是个比例项，在 6 个号的池子里
   `W_BASE=1.5` 只占约 1/5 的权重，耗尽号照样有稳定概率被抽中。实测把 `W_BASE`
   一路拉高，份额缓慢下降但**永远压不到 0**：

   | `W_BASE` | 330100178623 的份额 |
   |---|---|
   | 1.5（默认） | 14.4% |
   | 20 | 10.4% |
   | 50 | 9.7% |

2. **它被排在需要承重的第 2 层之后，而第 2 层当时是空操作。** `SLICE_S=30` 而每个号
   每轮都被用到，「最近 30 秒」必然覆盖全部账号，`cutoff = oldest + 30` 一个人也删不掉；
   再加上 `waiting or alive` / `sliced or alive` 两处兜底，第 2 层恒等于「什么都不筛」。
   所以第 3 层拿到的永远是**全量候选**，分级的意图根本没有机会表达。

**结论：「先用哪种钱」是资格问题，不是偏好问题，必须放在第 1 层。**
第一版那段「只进 Layer 3，绝不进 Layer 1」的理由（"月末会把只剩奖励积分的号全踢出池子"）
本身是对的，但由它推出的修法是错的。真正要防的是「全员耗尽时无人可用」，
而这只要把判据写成**分级**（"有人的时候才踢"）就自然满足了。

**现在的实现。**

- **第 1 层第 5 条（分级硬过滤，承重）**：`known` = 基础余额已知的候选。
  若 `known` 中有任何 `base > 0` → 只保留 `base > 0` 的账号，**基础余额未知的账号也保留**
  （不能因为没拉到余额就饿死它们）；若 `known` 全为 0 或为空 → 本层不生效，原样返回。
- **第 3 层 `base_share`（偏好）**：保留，只在同一级之内微调。
- **`runway` 仍用总余额**：用基础桶算续航会得出「奖励再多也马上没油」的假结论。

**实测效果**（生产参数、真实余额快照、6s 串行节拍）：

| 场景 | 基础>0 的 5 个号 | 330100178623 |
|---|---|---|
| 修正前（`W_BASE=1.5`） | 85.6% | 14.4% |
| 修正后（分级生效） | **100%** | **0%** |
| 修正后 + 全员基础耗尽 | 全池重新参与 | 全池重新参与（自动失效） |

**两个回滚开关，语义不同（别再混用）。**

| 环境变量 | 作用 | 是否真正的回滚 |
|---|---|---|
| `GATEWAY_ROTATION_BASE_PRIORITY=0` | 关掉第 1 层分级，回到「只按总余额加权」 | **是** |
| `GATEWAY_ROTATION_W_BASE=0` | 只关掉第 3 层的 `base_share` 偏好项 | 否，管不了资格 |

第一版曾把 `W_BASE=0` 当作整条策略的回滚开关，这是错的：它连「耗尽号该收缩多少」
都管不了（`base_share` 只是把它从 1/6 压到约 0.5/5.5）。


## 4. 为什么是这三层，而不是别的

- **为什么不用「最少使用优先」（Least-Used）**：它只看次数不看额度。
  一个剩 5 分的号和一个剩 5000 分的号，被用同样多次，池子续航最短。
- **为什么不用「纯随机」**：随机在**长期**上确实均匀，但短窗口内会出现
  「同一个号连中 3 次」——正是用户抱怨的现象。第 1 层的 `MIN_INTERVAL_S`
  直接消灭短窗口聚集。
- **为什么不用「一致性哈希」**：一致性哈希解决的是**缓存亲和性**，
  目标是「同一个 key 尽量落到同一个后端」。我们的目标恰好相反，
  而且要按额度加权，哈希帮不上忙。
- **为什么保留「失败换号」不改**：`report_failure` + `exclude` 已经是对的，
  主动分摊是**减少**触发它的概率，不是替代它。两者是纵深防御。

## 5. 持久化与重启

落盘位置沿用 `state/accounts.json`（`creds.save_store`），每账号新增三个字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `credits_spent_total` | float | 累计消耗积分（跨重启） |
| `requests_total` | int | 累计请求数（跨重启） |
| `last_used_wall` | float | 上次使用时间（wall clock，跨重启可比较） |

**为什么用 wall clock 而不复用 `cooldown_until` 的 monotonic**：`cooldown_until`
是进程内相对时间，重启后无意义；跨重启的「上次使用」必须用 wall clock。
两者并存，各管一段。

**写入节流**：`save_store` 在热路径上不能每个请求都重写文件。
采用「小间隔内跳过，除非 `force=True`」：热路径不带 force，
后台 `keeper()` 每 1800s 带 force 刷一次，进程退出时再 force 刷一次。
代价是崩溃最多丢一个小间隔的计数——这些计数只用于**加权排序**，
丢了只会让轮换短暂偏向，不会造成正确性故障。这是刻意接受的风险。

**不可持久化的凭据**（`persistable=False`，测试注入的假号）永远不落盘，
这条既有的安全约束不变。

### 5.1 reload 不能抹掉轮换记忆（2026-10-17 修正）

重载凭据后，账号对象被重建，reload 之前占坑、reload 之后那个请求早已不在的
**幽灵在飞计数**必须清掉（否则槽位被永久吃掉，`pick` 最终永远返回 None）。

但早期实现用的是 `RotationScheduler.rotate_state()`，它把每个号的 `last_used_at`
**一起归零**。后果是重载之后所有号同时变成「从未用过」：第 2 层的「最旧者」失去
参照，第 3 层的 `coolness` 对所有人同时变成 1.0。一次 `/admin/reload` 就抹掉了
「谁刚被用过」——而这只恰恰是轮换回答「该轮到谁」的唯一依据。实测 reload 之后
轮换表现退化成随机，而 `/admin/reload` 恰恰是最常被手动点的按钮。

修法：重载路径改调 `reset_inflight()` —— **只清 `in_flight`**，并用 `last_used_wall`
把 `last_used_at` 重新锚定到当前 monotonic 时钟（`age = now_wall - last_used_wall`，
于是 `last_used_at = now_mono - age`），保持「谁先谁后」的相对顺序。
`rotate_state()`（全量清空）仍保留，但只用于「全池画像彻底不可信」的场合，
并由 `Pool.reset_rotation_state_hard()` 显式暴露。

### 6.1 常量是拿真实流量校准过的，不是拍脑袋

用 `state/usage.jsonl` 里**真实**的 566 条非测试请求时间戳回放
（时间压缩 20 倍，保留相对间隔结构），验证 `MIN_INTERVAL_S` 各取值：

| `MIN_INTERVAL_S` | 服务数 | 拒绝数 | 拒绝率 | 公平度偏差 |
|---|---|---|---|---|
| `0.0` | 575 | 0 | 0.0% | 0.0099 |
| `0.5` | 575 | 0 | 0.0% | 0.0533 |
| `1.0` | 575 | 0 | 0.0% | 0.0128 |
| `2.0` | 575 | 0 | 0.0% | 0.0203 |
| `5.0`（默认） | 575 | 0 | 0.0% | 0.0429 |

真实到达间隔分布：`p25=0.98s`、`p50=2.35s`、`p75=5.53s`、`p95=20.19s`，
其中 **71.5% 的间隔小于 5s**。

**为什么 71.5% 的间隔小于 `MIN_INTERVAL_S` 却仍然零拒绝**：`MIN_INTERVAL_S`
是**每账号**的冷却，不是全池的。间隔 < 5s 只意味着「上一个用过的号」还不能再用，
但 3 个号轮转，下一个请求完全可以从**另一个**号上服务。只有**所有**号都在
5s 窗口内才会拒绝。实测该条件下 566 条请求零拒绝，因此 5s 默认值成立。

**一个必须记住的容量边界**：`MIN_INTERVAL_S=5` × 3 账号 ⇒ 稳态上限
`3 req / 5s = 0.6 req/s`。账号数越少这个上限越低；若未来压测出现 503，
先调 `GATEWAY_ROTATION_MIN_INTERVAL_S`，再考虑扩池。这是**抗薅羊毛的代价**，
是刻意的限速而非缺陷。

`tests/test_rotation.py`（离线，不耗真实积分）必须覆盖：

`tests/test_rotation_state.py`（离线）必须覆盖：

15. `rotation_policy()` 在有无 env 覆盖时都返回合理值，含 `MIN_RATE` 钳制。

**认领/释放回归（§2.1 的两个坑，必须有独立断言）**：

16. **耗尽断言（锁住「必须释放」）**：3 账号、cap=2，**不释放**地连续 `pick()`，
    必须在第 `3 × cap` 次后返回 `None`——这条断言证明「占坑/释放配对」是承载逻辑的，
    而不是可选的记账。若有人日后把占坑删掉，本项会立刻失败。
17. **不泄漏断言**：同样的循环但**每次释放**，500 次内 `pick()` 返回 `None` 的次数
    必须为 `0`，且结束时所有账号 `in_flight == 0`。
18. **无条件释放**：只调用释放、**从不调用** `note_request_started`，
    500 次内也必须零 `None`、结束时 `in_flight == 0`（对应 §2.1 的坑 2）。
19. **幂等**：对同一账号连续释放 5 次，`in_flight` 必须是 `0`，绝不为负。
20. **并发上限（barrier）**：N=16~24 线程同一 `Barrier` 释放，跑完整
    `pick → 认领 → 释放` 循环，单账号并发峰值**不得**超过 `MAX_CONCURRENCY`。
    （缺陷期实测：cap=2 时峰值达 8；修复后为 2。）
21. **公平度（真实参数）**：cap=2、3 等额度账号、200 次含释放的 `pick()`，
    各账号占比偏差 ≤ 0.05，且零 `None`。

**2026-10-17 修正新增的钉子**（都是「第一版看起来对、实测失效」的场景）：

| # | 断言 | 防的是什么 |
|---|---|---|
| 22 | 生产参数（`MIN=5s`、`SLICE=30s`）+ 真实余额快照 + 6s 串行节拍 400 次，基础套餐已耗尽的号命中 **0** 次 | 第一版把分级写成权重，实测耗尽号仍占 ~16% |
| 23 | `base_priority=False` 时同一个号**重新**分到流量 | 证明 22 是分级的功劳，不是别的巧合 |
| 24 | 全员基础耗尽时每个号仍然分到请求 | 「优先」不能被写成「只准」 |
| 25 | 只有等满 `W` 的号进入 `_waiting`；都没等够时为空且仍能选出号 | 旧判据用 `MIN_INTERVAL_S`，在 N 号池里恒真 = 空操作 |
| 26 | `_time_slice` 的收窄结果非空，且 `last_used_at` 被污染为 NaN 时退回最久未用的那个 | `sliced or alive` / `waiting or alive` 兜底把收窄吞掉 |

> （400 次里 55 次落到耗尽号上）。

## 8. 风险与已知取舍

| 风险 | 缓解 |
|---|---|
| 在飞计数泄漏 → 池子永久变小 | 所有路径 `finally` 释放；**释放无条件于 `started`**；并发冒烟测试；`snapshot()` 暴露 in-flight 便于观测；§7 第 16~19 项断言 |
| **并发上限 TOCTOU**（已发生） | 检查与占坑在同一临界区（`pick()` 内）；barrier 测试断言单账号峰值 ≤ 上限 |
| **双重计数**（已发生） | `note_request_started` 只做镜像对齐，权威计数在调度器；见 §2.1 |
| **`coolness` 未钳制导致权重为负**（已发生） | 钳制到 `[0,1]`；见 §3 第 3 层注释 |
| 加权随机不可复现 → 难调试 | 注入 `random.Random` 种子；`pick` 附 `reason` 说明为何选中 |
| 节流导致崩溃丢计数 | 只影响排序，不影响正确性；退出时 force 刷 |
| 第 2 层在高并发下过度收窄候选 | 保留兜底（§3 第 1 层末）；`explore=True` 可绕过 |
| 新增落盘字段破坏向后兼容 | `load_store` 容错解析，缺字段走默认；已有 `.bak` 文件可回滚 |
| 误把保护约束降级为权重 | 第 1 层硬过滤是设计红线，单测锁定 |
| **限速导致 503**（换成新症状） | 用真实流量校准过常量（§6.1，566 条请求零拒绝）；`MIN_INTERVAL_S` 可调；文档明示容量边界 |
